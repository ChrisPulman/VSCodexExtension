Additional fixes register a turn before sending `turn/start`, preserving responses delivered in the same stdout chunk as the start response. The bridge sends `initialized`, shares startup between callers, correlates responses, fails pending operations on disconnect, and waits for response writes. The C# bridge serializes writes and startup and completes outstanding requests when the process output closes. Dispatched turn failures surface for user review instead of automatically replaying potentially completed edits through another transport. Startup failures can still use the fallback path.

The additional active-writer conflict reported in [#94's comment](https://github.com/ChrisPulman/VSCodexExtension/issues/94#issuecomment-5638685973) is covered explicitly: after app-server initialization succeeds, thread start/resume errors are returned rather than retried through the SDK. A locally active thread is rejected before another resume RPC. This prevents a second writer being created by transport failover; it does not forcibly unlock a thread owned by another Codex process. The actionable conflict remains visible. The follow-up approval report in #52 is covered by the same typed request-ID and structured form fixes as #95/#107.

The existing ReactiveUI 26 package references were incompatible with the older System.Reactive command/scheduler usage. The matching `.Reactive` packages retain those contracts without downgrading. Native VS2026 testing then exposed a second mismatch: `ReactiveUI.Extensions` 4 targets Rx 6.1, while the other reactive assemblies target Rx 7. Visual Studio resolves the former through its own Rx 6.1 binding policy, causing a missing scheduler-method exception. Standard Rx 7 `ObserveOn`, `Throttle` and `DistinctUntilChanged` operators replace those helpers, and the conflicting dependency is removed. A VSIX metadata regression test checks every packaged assembly's Rx reference against the packaged Rx version. The VSIX contains the runtime dependencies and required ReactiveMemory payload.
