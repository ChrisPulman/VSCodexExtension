# Codex Desktop parity and Visual Studio integration proposal

Audit date: 2026-10-23. This is an implementation assessment and proposal, not a declaration of full parity. The five open issues now have source fixes and automated regression coverage; native IDE acceptance remains incomplete. See [issue resolution and validation](ISSUE-RESOLUTION.md).

## Integration boundary

The extension already runs a local Codex app-server through `Resources/codex-bridge.mjs`, with SDK and CLI fallback paths. Keep this foundation. OpenAI recommends app-server for product integrations requiring persistent conversations, streamed activity, interruption, tools, and approval handling; the application owns its surrounding workflow and UI. [OpenAI integration guidance](https://developers.openai.com/blog/codex-as-a-platform)

Desktop app tools available in the audit environment expose additional application-owned features: managed worktrees, chat organization, automations, connected hosts, shared links, plugins, browser panels, document editors, and media previews. Their presence in this Codex session does **not** make those tools a public API available to this VSIX. Classify each implementation as app-server protocol, Visual Studio host service, local extension feature, or separate service requiring a documented integration. Never advertise an unavailable remote capability merely because a similarly named local command exists.

The coordinating agent also inspected the running desktop app through Codex Computer Run: its visible layout includes a project sidebar, chat search/history, permission/model/effort controls in the composer, and a right sidebar for changes, agents and sources. Use these as concrete interaction references when designing the VS tool window, with native VS commands and docking where appropriate.

## Recommended architecture

Compose independent services behind the existing Core contracts. Keep IDE automation on a thin host boundary and avoid inheritance-based feature stacks. A chat coordinator should depend on typed transport, repository, settings, context, review, and notification interfaces; the WPF view model should compose their observable state.

1. **Protocol adapter:** evolve the current bridge into a versioned app-server adapter with typed requests/events, explicit negotiated capabilities and one owner for process lifecycle. Route every response and event by thread, turn and request IDs. Distinguish failed/interrupted/completed outcomes. Keep transport fallback explicit because fallback can reduce features and must not replay side effects invisibly.
2. **Application state:** separate app-server thread identity from local display metadata, queued work and recovery checkpoints. Add migrations and transactional persistence before archive/fork/pin. Scope state and active turns to immutable workspace identities.
3. **VS host services:** compose document/selection, solution/project, diagnostics/build, navigation, diff and terminal adapters. Use live IDE buffers where available; disk context alone can omit the changes the user is editing. Capture current solution configuration and target framework with diagnostics.
4. **Repository service:** introduce worktree lifecycle and reviewed Git actions independently of chat transport. Track ownership and dirty state; retain recoverable work when archiving. Connect the result to VS solution opening and repository context.
5. **Optional integrations:** place automation scheduling, remote hosts, plugin accounts and artifact viewers behind capability checks. Provide an honest unavailable state until a public service contract and end-to-end implementation exist.

The bridge now sends the initialize/initialized handshake, shares startup across concurrent callers, fails requests on disconnect, registers turns before dispatch to retain immediate output, and avoids automatic replay after a dispatched turn fails. Continue auditing against the deployed protocol version. `model/list` can be a catalog rather than proof of account entitlement. [App-server integration and account caveats](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)

## Modern properties environment

Keep one typed settings schema, validation rules and effective-value resolver for both hosts. Define stable IDs, category, label, description, type, default, scope, restart requirement and supported-version metadata. Compose UI adapters over that schema; do not build another independent store for each UI.

Recommended categories are Account and Runtime; Models and Execution; Approvals and Sandbox; Projects and Context; Skills and MCP; Agents; Git and Worktrees; Automations and Notifications; Appearance and Accessibility; and Diagnostics. Unsupported categories should explain availability, not present inert switches.

| Option | Benefit | Cost / decision |
| --- | --- | --- |
| Existing VSSDK host plus optional unified settings adapter | Retains WPF/COM solution integration and VS2022 compatibility while adding the modern host experience | Recommended incremental route. Confirm API/runtime availability, manifest schema and legacy loading before raising SDK dependencies. |
| Migrate to VisualStudio.Extensibility | Declarative settings with typed validation and observable values; modern process model | Broader migration of tool windows and host integrations. Prototype first; settings alone do not justify a rewrite. |
| Custom WPF options page only | Consistent controlled UI across both IDEs | Useful fallback, but not unified settings integration; must supply its own search, validation and accessibility. |

Microsoft exposes `ProvideSettingsManifestAttribute` for in-process unified settings registration and `ProvideSettingsObserverAttribute` for change observation when the service is available. These support investigating an adapter without assuming every VS2022 runtime has the same API surface. The observer reference includes prerelease caveats. [Shell registration API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualstudio.shell?view=visualstudiosdk-2017), [settings observer API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualstudio.shell.providesettingsobserverattribute?view=visualstudiosdk-2022)

The separate VisualStudio.Extensibility settings API supports typed definitions, validation, effective values, subscriptions and generated observers; the retrieved documentation marks settings experimental. Treat this as a compatibility spike, not an automatic package upgrade or a reason to suppress warnings. [Settings API overview](https://learn.microsoft.com/en-us/visualstudio/extensibility/visualstudio.extensibility/settings/settings?view=vs-2022)

Local VS2026 implementation evidence was read from `C:\Program Files\Microsoft Visual Studio\18\Enterprise\Common7\IDE\UnifiedSettings\registration.schema.json`, `PublicAssemblies\T4Settings.registration.json` and `Extensions\Community\WebProjectsOptions.registration.json`. The shipped schema uses top-level `properties` and `categories`, stable dotted IDs, typed defaults and migration metadata. The T4/Web Projects examples associate a category with `legacyOptionPageId` and migrate registry values using `VsUserSettingsRegistry`. VSCodex currently stores its settings in JSON, so copying their registry migration paths would not migrate VSCodex settings: implement and test a deliberate first-run import instead.

For old VS2022 hosts, avoid putting new unified-settings types in unconditional base package signatures or eagerly initialized fields until binary loading is proven. Isolate the adapter and load it after host capability detection, or ship a version-targeted adapter package if required. Retain the existing DialogPage GUID and fallback. A successful build against SDK 17.14 alone does not establish binary compatibility with the manifest's declared VS17.0 minimum.

Use precedence of explicit turn override, workspace override, user default, then schema default. Keep credentials out of shareable settings. Migrate current JSON settings once with a schema version, rollback copy and preserved unknown fields. Avoid writing workspace execution defaults back into every workspace when a user intended a local override. Subscribe once, dispose subscriptions, and prevent feedback loops between UI adapters.

Visual Studio 2026 provides searchable settings, user/solution scope and JSON editing; settings imported/synchronized from VS2022 do not synchronize back to VS2022. Preserve extension migration semantics explicitly rather than relying on host profile synchronization. [Visual Studio settings](https://learn.microsoft.com/en-us/visualstudio/ide/visual-studio-settings?view=visualstudio)

For both VS2022 and VS2026, install the built VSIX into a clean experimental instance, verify package load and tool-window activation, run a real thread, approve and decline requests, switch/close/reopen solutions during work, reload persisted chats, edit settings through each supported surface, and check Light/Dark/High Contrast, keyboard-only navigation, screen reader labels and 100/150/200% DPI. ## Implemented local parity slice (2026-10-23)

The history panel now includes an explicit **Refresh Codex threads** action. It uses the same owned bridge/app-server process as conversations and requests every `thread/list` page, deduplicates by server identifier and rejects repeated pagination cursors. It imports only an exact working-directory match for the current workspace. **Include archived** permits importing and displaying archived threads. Opening a catalog-only thread reads persisted turns before showing it; only user and assistant text is reconstructed for the local transcript. Tool history remains on the server rather than being invented from text.

**Fork** invokes `thread/fork` and saves the returned new server identifier. It preserves the server-side conversation context for later turns. **Archive/restore** invokes the corresponding public protocol method before changing local metadata; failure leaves the local archive state untouched. These mutation requests are never rerouted through SDK/CLI turn fallback, avoiding a duplicate mutation or an accidental prompt submission. **Pin/unpin** persists an extension-local preference and sorts those entries first. Local rename and delete retain their previous semantics and do not rename/delete server threads. JSON persistence now serializes before touching the destination and atomically replaces from a same-directory temporary file; serialization failures preserve the last complete document. Catalog timestamps are preserved instead of making every refresh appear as fresh chat activity. Existing JSON history migrates naturally with absent pin/archive properties defaulting to false; no server identifiers are reused across local workspace-copy operations.

The toolbar **Review active file** action opens Visual Studio's native diff document with a Git HEAD baseline on the left and the active editor file on the right. It uses the VS17 SDK service and does not require a new VS2026-only dependency. The Git baseline is copied as bytes, preserving its encoding; Git object syntax relative to the working directory supports solutions nested below a repository root. Snapshot files are marked temporary for the VS difference service. The service supports the running document table; native verification must still confirm dirty-buffer behavior, encoding and theme/DPI on the actual IDE. [VS difference service](https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualstudio.shell.interop.ivsdifferenceservice.opencomparisonwindow2?view=visualstudiosdk-2022), [temporary-file options](https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualstudio.shell.interop.__vsdiffserviceoptions?view=visualstudiosdk-2022)

Activity sections for agents, tools, MCP, skills and files start collapsed. Streaming assistant content starts expanded. At completion, the shared `ResponsePresentation` policy collapses earlier assistant text and trailing empty nodes, then reveals the last nonempty response and its ancestors. It preserves the user's expansion choices in tool sections. This also fixes a hidden-final-summary case when the assistant section was collapsed during streaming. Behavioral TUnit coverage exercises collapsed ancestors, earlier commentary, a trailing empty stream and completion with no text. Native tree rendering and accessibility still require host acceptance.

Protocol parameter shapes were checked against the installed Codex CLI's generated public TypeScript (`codex app-server generate-ts`), including `ThreadListParams`, `ThreadReadParams` and `ThreadForkParams`. `ThreadCatalogTests` executes the packaged JavaScript adapter against an in-memory RPC endpoint, covering pagination and deduplication, archive filters, persisted-turn reads, fork identity, archive/unarchive method selection, rejected missing identifiers/repeated cursors and no replay of failed mutations. Build/test results are recorded by the coordinating verification run in [ISSUE-RESOLUTION.md](ISSUE-RESOLUTION.md); the existence of these tests does not establish a live-account or native-IDE pass.

The extension-owned Worktrees panel now lists Git checkouts, creates isolated `CP_` branches and persists ownership/pinning. Archive captures file contents including ignored files, index and HEAD before parking the checkout; restore moves the retained checkout back. It refuses primary/current/unowned, locked or pinned targets and unsupported nested repositories/submodules/link paths. Archive retains a checkout and recovery snapshot rather than reclaiming disk. Open launches the file browser, so solution switching and independently isolated agent execution are still separate work. This local implementation does not establish remote Desktop handoff parity. The [local automation scheduler](AUTOMATIONS.md) now saves workspace prompts and intervals, initially paused until explicitly enabled. It polls only while the VS tool window is loaded, runs each overdue job once after downtime, checkpoints the next due time before launch and prevents overlapping passes. Independent CLI jobs use the configured default model, read-only sandbox and no interactive approvals, with a 15-minute timeout and cancellation on extension shutdown. Latest response/error and unread state are saved atomically. The local notification list is narrower than a Desktop inbox and cannot wake Visual Studio or run in the cloud. No private Desktop scheduler/worktree service is assumed available to the VSIX. Browser, artifacts, account/plugin connection, remote/cloud/mobile and shared-link workflows still require documented service contracts or independently implemented local host features.
