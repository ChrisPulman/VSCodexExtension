# Managed local worktrees

Open the tool panel's **Worktrees** tab and select **Refresh** to list the current repository's primary, external and extension-owned checkouts. Enter a new `CP_` branch name and select **Create** to create a separate checkout from the current workspace's committed `HEAD`. Uncommitted source changes are not copied into the new branch. **Open folder** opens the checkout in Explorer; open its solution or folder in another Visual Studio window to work there. The current chat's workspace is never switched implicitly.

**Pin / unpin** protects an owned checkout from archival. For a checkout shared with another application or person, protect it using `git worktree lock --reason "shared checkout" <path>`; VSCodex refuses all Git-locked worktrees. External and primary checkouts are listed for discovery but never managed or moved.

**Archive / restore** parks an extension-owned checkout under the extension's archive directory, or moves it back to its original managed location. Archiving retains the checkout and does not reclaim disk space. Before each move, VSCodex copies and SHA-256 verifies all regular working files, including untracked and ignored files, and copies the Git index and records HEAD. A post-move check verifies the working files and the exact staging index again. Git's worktree move preserves the existing branch, staged changes and working files without commits, stash, reset, force or removal. Recovery snapshots remain under `%LOCALAPPDATA%\VSCodex\managed-worktrees\snapshots`; they can contain ignored files and should be treated with the same privacy as the source checkout.

Active, primary, pinned, unowned, Git-locked and submodule-containing checkouts are refused. Embedded repositories and reparse points (links/junctions) are refused because independent recovery cannot be guaranteed. Git errors, registry corruption, concurrent edits detected during verification, occupied destinations and storage failures are surfaced in the tool-window status. Existing data is retained. Registry writes are atomic, operations use an exclusive cross-process lease, and pending move destinations are persisted before Git runs so a subsequent refresh can reconcile an interrupted operation with Git's actual registered location.

If a move completes but the verification reports a concurrent edit, inspect the visible checkout and the retained snapshot before retrying; no checkout is deleted. The snapshot's `files` directory contains the copied working bytes, `index` contains the staged state, `head.txt` identifies the base commit, and `manifest.json` contains the file hashes. Snapshot retention is deliberate and automatic deletion is not provided.
